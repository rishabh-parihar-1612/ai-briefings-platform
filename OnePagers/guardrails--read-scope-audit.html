Read-Scope Audit

Read access is a permission too · guardrails › read-scope-audit

coremixed confidence2026-09-13

Hook

Read access is a permission too — an agent doesn't need to be issued a credential to misuse one; it only needs a search tool that can find it.

Mental model

Write scope is the lock on the vault door; read scope is every hallway the agent is allowed to walk. Audit only the vault and you miss the hallway that dead-ends at an unlocked drawer.

Decide

Use when read access is broad
  • The agent's search/read tool spans more than its assigned task's file or repo scope
  • Secrets or tokens live in plaintext anywhere that scope reaches
  • Nobody can name every credential the read tool could surface today
Skip when read scope is already provably narrow
  • The read tool is hard-scoped to a single validated subdirectory or dataset
  • No credential of any kind exists inside the agent's reachable read path
  • Read access is enumerated, versioned, and reviewed on the same cadence as write access

Aryaka

An Aryaka NetDevOps remediation agent is issued a write-scoped tool limited to tunnel restarts on one PoP under investigation. Its search tool, though, points at the shared ops-tools repo for convenience, since on-call runbooks live there too. A .env left by a migration script eighteen months ago holds a token scoped to the SD-WAN orchestrator's tenant-wide config API — reachable across all ~40 PoPs, not just the one being triaged. Assumption: a misapplied config push takes roughly a minute per PoP to detect and roll back, so a token nobody audited sits reachable across every PoP the whole time it goes unnoticed. Scoping the search tool to the PoP-specific subdirectory removes that token from the agent's reach entirely — independent of whether anyone is watching.

Say this

I audit what my agent's search tool can read, not just what its write tool can do — a credential doesn't need to be issued to be misused, only discoverable.

Trap

Auditing only what the agent was issued, never what its read tool can reach. The tell: you can name every write permission but can't answer, in under a minute, what the agent's read scope could hand it.

Probe

What's the distinct failure shape this card adds beyond "the agent held a destructive credential it shouldn't have" (e.g., Replit's July 2025 database deletion)?
Show answer

An agent can misuse a credential it was never issued at all — discovered via read/search access broader than its task, not one it held outright. Auditing only issued write permissions misses this; only auditing what the read tool can actually reach catches it.

Why doesn't "don't touch production" as a system-prompt instruction, or a human-approval gate, close this gap?
Show answer

Both sit on top of the same unanswered question: does the agent structurally hold or reach the credential at all? An instruction is words, not enforcement; an approval gate degrades toward rubber-stamping past roughly a 95% approve rate. Neither removes the credential from the agent's reachable surface.

What's the one-line design-review question this source adds to a guardrails review?
Show answer

"Can you name, in one sentence, every credential this agent's read scope could surface today?" If not, the read side of the authorization boundary hasn't been audited — only the write side has.
