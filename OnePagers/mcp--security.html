MCP Security & Governance

Blast radius equals credential scope · mcp › security

corehigh confidence2026-09-03

Hook

The protocol did what it promised. The privilege model was the defect. Three of four named incidents were injections through authorized reads, converted to action by over-scoped credentials.

Mental model

An MCP server is not a service you call. It is code you run with your credentials that writes into your model's context — so installing a random one is plugging in a USB-C stick you found in a parking lot.

Decide

Use when a third-party server may join the allowlist
  • A human read its code, and the version is pinned by hash
  • It runs containerised, with no ambient credentials
  • Read-only credential, or the write is gated
Skip when say no, and plan for shadow MCP
  • Write-capable and nobody owns the approval gate
  • It would inherit a developer's own laptop identity
  • No audit log to answer "what did it do"

Aryaka

Getting past security review. Security blocks the rollout. Take in three things, none of them your opinion: a filled OWASP MCP Top 10 table — one row per MCP01–MCP10 with our control, or a named accepted-risk owner; the NSA CSI of 20 May 2026; and the shadow-MCP argument — say no and ~30 NetDevOps engineers run servers on laptops that sit inside the VPN with their own cloud profiles.

Ask for: a reversible pilot. aryaka-inventory, one read-only tool, one engineer, four weeks, review date agreed. Human sees: every tool call logged against a non-human principal. Concede: no write-capable server on the allowlist for the first quarter.

Breaks when: the sanctioned path is slower than pasting a config. Governance dies of friction; a one-command install from an internal registry is the fix.

Say this

The choice isn't MCP versus no MCP — it's governed MCP versus shadow MCP. Security and scale aren't opposites; the guardrails are what let us say yes.

Trap

Vetting the server and stopping there. The tell: every control you can name describes the server, and none describes what it may do with what it finds — so the GitHub exfiltration reproduces with a perfectly well-behaved server.

Probe

A local server "only reads public docs." Why is it still your highest-exposure install?
Show answer

It runs with the developer's credentials and network position — inside the VPN, with their SSH agent and cloud profile. "Only reads" describes the server's tools, not the process's ambient authority. Run third-party servers containerised, pinned by hash, with no ambient credentials.

The harness already marks retrieved content as data. Why must the write gate exist anyway?
Show answer

Prompt-level defences are probabilistic and the write is not recoverable, so the two controls have to be independent. The harness renders server output as delimited, non-authoritative data; the gateway gates open_cr regardless of what the model concluded, and shows the concrete artifact rather than a summary of intent.

Asana's server was official and verified. What did that incident actually prove?
Show answer

That preference is not a control. Launched 1 May 2025, cross-tenant bug found 4 June, MCP disabled 5–17 June, ~1,000 customers — root cause was failing to re-verify tenant context on cached responses. Scoped credentials and tenancy enforced by a hard server-side predicate reduce blast radius; publisher reputation does not.
