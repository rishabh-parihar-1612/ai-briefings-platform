Scoped, Time-Boxed Agent Credentials

Resource scope and time scope are different axes · cloud-coding-agents › credential-model

supportingmixed confidence2026-09-13

Hook

A read-only token that never expires is still a live risk months later. Resource scope and time scope are different axes — most teams design only one of them.

Mental model

A cloud sandbox with a developer's full ambient access is the laptop problem in a new location. The fix adds a second axis to "which resource": a hard expiry, independent of task completion.

Decide

Use when an agent touches anything beyond its own sandbox
  • The task reads logs, a database, or any API outside the sandbox
  • A task could plausibly run longer than its stated purpose needs
  • More than one team member's data is reachable from one identity
Skip when nothing beyond the sandbox is ever touched
  • Every action stays inside the disposable sandbox itself
  • The resource is already public or has no meaningful blast radius
  • No prior incident or near-miss has justified the design cost yet

Aryaka

A diagnosis agent given a NetDevOps engineer's own SSH keys and VPN session inherits access to every customer tenant that engineer can reach, because engineers are provisioned broadly for on-call flexibility — one tenant's ticket, every tenant's exposure. The same agent, run in a sandbox with an OIDC token scoped to one tenant's read-only telemetry API for 30 minutes, cannot reach the other tenants even if a prompt injection or a hallucinated tool call tries to point it there. When the clock runs out, the task either finishes, re-requests a fresh token through the same approval gate, or hands off to a human — a task that silently needs hours of standing access is itself a signal it was scoped wrong from the start.

Say this

The comparison that matters isn't "sandbox vs. no sandbox" — it's what the credential can reach and for how long. Scope by resource and time, or you've just relocated the laptop's blast radius.

Trap

Treating "read-only" as the whole safety argument. The tell: nobody can say when the token expires, only what it can reach — a read-only grant with no expiry is still a live risk months after its task is forgotten.

Probe

Your agent's credential is read-only and scoped to one database. Is that sufficient?
Show answer

Not on its own. Resource scope answers "which system"; time scope answers "for how long." A read-only token with no expiry is still a standing risk months later — the same failure shape as an unrevoked laptop credential, just narrower in what it can touch.

A task's OIDC token expires before the task finishes. What should happen?
Show answer

The task re-requests a fresh token through the same approval gate, or hands off to a human — the expiry is a forcing function for re-authorization, not an outage. A task that silently needs standing access for hours is a sign it was scoped wrong, not a sign the expiry was too short.

How does this credential model differ from the rate/aggregate quotas covered under deep-agents?
Show answer

They're separate axes that both matter. Rate/aggregate caps the volume of an action within a session ("one email is fine, a thousand is an incident"); time-boxing caps the window in which any access exists at all, regardless of how much was done inside it. Neither substitutes for the other.
