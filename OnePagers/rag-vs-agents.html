RAG vs Agents — The Decision Boundary

Two axes, not a vibe about loops · rag-vs-agents

supportingmixed confidence2026-09-10

Hook

RAG is bounded read over data you own. An agent is unbounded read plus write over data you don't.

Mental model

Two independent axes decide it: data ownership/volatility, and read-only vs. write. Only the write-plus-not-owned cell justifies a full agent loop — the other three are cheaper and testable.

Owned+read=RAGNot-owned+read=Tool callOwned+write=Gated workflowNot-owned+write=Agent

Anatomy

PieceDoesFails when
Owned, read-onlyIndex it, retrieve, answer — RAGAnything more than retrieve+generate is over-engineering
Not-owned, read-onlyOne or two deterministic tool calls the model chooses betweenA loop gets added when the number of calls is actually known
Owned, writesDeterministic workflow, model fills parameters, human/policy gateThe read path's permission model gets silently reused for the write
Not-owned, writesThe only cell that justifies a full agent loopRead-safety reasoning gets extended to cover a write action too
"Just add a retrieval loop" objectionIterative RAG: closed action space, predefined flow, nothing irreversibleAny loop at all is treated as proof of "now it's an agent"

Numbers

1 vs. 5–8Model calls per query: RAG (retrieve+generate) vs. an agent loopThe base unit for the cost argument against defaulting to agents
~15×Anthropic's multi-agent research system's token use vs. a single chatThe direction to carry into a design review, not the exact multiple

Decide

Use when
  • Deciding whether a new system needs an agent loop or a simpler RAG/workflow/tool-call shape
  • A team is about to rebuild a working RAG system into an agent over one new write action
  • "Agentic RAG" is used as if it names a third architecture distinct from agents
Skip when
  • The action space is already known to be closed and single-typed
  • All writes in scope are already gated by a deterministic workflow, not model judgment
  • The system genuinely needs an unknown number of steps over data nobody owns

Aryaka

"Why did the Bangalore branch drop the SD-WAN overlay at 02:14" decomposes into 5 sub-questions across the grid: runbook meaning (RAG, owned wiki), tunnel telemetry at that timestamp (one deterministic query tool, volatile data), a change-window check (deterministic tool), carrier status (external API), and opening a carrier ticket or rolling back config (gated write). Four of five are read-only with a known lookup set — the right build is RAG plus three fixed-order tools, never a general agent loop. Built as an open agent instead: 400 requests/day at 6 calls each is 2,400 model calls/day, a 3× cost multiplier for zero added capability.

Say this

In RAG the model is an answer compiler; in an agent it's a decision maker. The test isn't the loop — it's whether the data is volatile or not yours, and whether the action writes state.

Trap

Rebuilding a working RAG system into a full agent because it needs to iterate on retrieval. The tell: the action space is still closed, the data is still owned and static, and nothing about the loop can be wrong irreversibly.

Probe

A RAG system retries retrieval if the first pass didn't return enough context. Does that make it an agent?
Show answer

No — the action space is still closed (only ever queries the same index), the data is still owned and slow-changing, and a bad retry costs tokens, not an irreversible action. It's iterative RAG; the model is still an answer compiler, not a decision maker.

A team says "agentic RAG" is a distinct third architecture between RAG and agents. How do you respond?
Show answer

Architecturally, no — once retrieval is one tool a decision loop may call, the system is an agent whose tool set includes a vector search. The term is still useful as a label for a migration path (a RAG system evolving into a loop), not as a description of the architecture.

A system reads owned, static policy data and also resets passwords and opens tickets. Should the whole thing become an agent?
Show answer

No — split it. RAG or a fixed workflow handles the read/answer path; writes get a small, explicitly enumerated set of gated actions. Two write actions shouldn't justify rebuilding the whole system as an agent, importing the loop's failure modes into the 90% that was just a question.
