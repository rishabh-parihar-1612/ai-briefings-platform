Agent Failure Debugging

Localize before you optimize · debugging

supportinghigh confidence2026-09-10

Hook

"It gave a wrong answer" isn't a diagnosis. Localize to one of ten stages first — generation is the last stage to blame, not the first.

Mental model

Localization speed is a property of trace design, not investigator cleverness. Freeze the incident, classify inner/middle/outer, localize the stage, then replay and substitute known-good values before touching a single prompt.

Anatomy

PieceDoesFails when
Three loopsInner=execution, middle=knowledge/retrieval, outer=version regressionOnly one loop gets checked, missing the other two failure classes
Ten-stage taxonomyscope→memory→retrieval→context→planning→tools→policy→generationGeneration gets blamed first instead of last, on no evidence
Trace designStores assembled context per turn, not just the templateCan't tell "retrieval missed" from "model ignored what it retrieved"
Deterministic replayRecorded outputs replayed through the same harness, zero new tokensReproduction is attempted by rerunning live, on a nondeterministic system
Counterfactual attributionSubstitutes one stage's output with a known-good value, re-runsA causal story is asserted ("retrieval looked wrong") instead of tested
Composition / seam failureEvery component passes; the combination still misses a distinctionThresholds get tightened until a component test "catches" a one-off case

Numbers

10 stages, 1 tableA wrong-answer symptom maps directly to exactly one stageLocalizes a failure in minutes, not an afternoon of guessing
3 silent moversModel version, prompt (console edit), corpus snapshotThe dependencies that change behavior without anyone calling it a deploy
4 distinct valuesRetrieved ≠ selected ≠ placed-in-context ≠ actually-usedA system recording only the first can't say which one failed
0 new tokensCost of deterministic replay against recorded model outputsTurns a trace store into a zero-token regression suite

Decide

Use when
  • An agent's wrong answer needs root-causing, not just a retry
  • Quality dropped and nobody can say what changed
  • Individually-passing components still produce a bad product
Skip when
  • The failure is a one-off with no trace captured at all — fix the trace first
  • No version block exists yet — build that before the outer loop
  • The system hasn't shipped a wrong answer worth this investment yet

Say this

Localize before you optimize. The model's final answer is not the source of truth for what happened — the trace is, and generation is the last stage to blame, not the first.

Trap

Diagnosing a wrong answer by reading the final answer and tuning the prompt. The tell: nobody checked whether the retrieved evidence ever entered the model's context at all — "retrieved" and "actually used" are different facts, and only one got verified.

Probe

An agent's answer is wrong. What's your very first action, before any investigation?
Show answer

Freeze the incident — preserve the run ID, every version, the full trace, and current state before touching the prompt. Editing the prompt first destroys the evidence for whatever the actual root cause turns out to be.

You believe retrieval caused a wrong answer. How do you prove it rather than assert it?
Show answer

Counterfactual attribution — substitute the retrieval step's output with a known-good value and re-run the rest unchanged. If the answer becomes correct, retrieval is a strong causal suspect; if it doesn't, retrieval was never the cause, and that negative result is worth as much as a positive one.

Every component passes its own tests, but the end-to-end product is still wrong. What class of bug is this?
Show answer

A composition/seam failure — retrieval, planning, tool use, and generation can each be individually defensible and still combine to miss a critical distinction. The fix is a seam eval ("given A's output, does B interpret it correctly?"), not tightening a component's test.
