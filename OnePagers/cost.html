Token Economics & Cost Levers

Output costs 3-5x — attack decode, not prefill · cost

supportingmixed confidence2026-09-10

Hook

Output tokens cost 3–5× input tokens because decode is memory-bandwidth-bound and serial — that one fact explains most of what you observe in production latency and cost.

Mental model

Prefill is parallel and compute-bound; decode is serial and memory-bound. Attack the two separately, then work the cost lever stack from the top down before touching model choice.

Decide

Use when run the lever stack before touching the model
  • Spend is dominated by a handful of mechanical, high-volume steps
  • A stable system prompt or tool catalog is re-sent on every call
  • Nobody has checked whether prompt cache hit rate is actually non-zero
Skip when the arithmetic doesn't justify the effort
  • Volume is low enough that absolute spend is immaterial
  • The workload is already Batch-API-eligible async work at floor cost
  • A single model call per request with no retrieval or tools exists

Aryaka

NetDevOps support assistant at 10,000 requests/day, ~3 model calls each: naive cost runs comparable to the Edge Playbook's $60K/month shape. Routing classification and RCA-drafting to a small model (5 of 8-call-equivalent steps), a stable runbook-and-tool-schema prefix cached at a real >0% hit rate, and capping mechanical steps' output brings the same workload toward $19–22K/month — a ~3× cut with no accuracy loss, verified against the existing eval suite before shipping. The most common single fix: a ticket ID at the top of the system prompt was killing 100% of cache hits.

Say this

I'd instrument cost per successful task, not cost per request — they diverge sharply, and the gap between them is your reliability bill, not a pricing problem.

Trap

Optimizing prompt size to fix a slow response. The tell: the response is slow because of output length (TPOT), not prompt size (TTFT) — trimming the prompt does nothing to decode time.

Probe

Why do output tokens cost 3–5× input tokens across nearly every provider?
Show answer

Prefill (processing the prompt) is parallel and compute-bound; decode (generating output) is serial, one token at a time, and memory-bandwidth-bound. Decode genuinely costs more to serve — it isn't arbitrary pricing, and it's why capping output length is the single best latency lever.

A team put a live timestamp in the first line of the system prompt for observability. What did that actually cost them?
Show answer

100% of prompt-cache hits, because caching is an exact prefix match and the timestamp sits at position zero — every request after it invalidates the cache. The system still works, so nobody notices; it just costs 5–10× more than it should until someone checks the hit rate.

A round-robin load balancer serves a cacheable workload across 8 replicas. What's the actual hit rate, and what fixes it?
Show answer

Roughly ~12%, versus ~95% achievable, because each replica only caches what it happens to see. Cache-aware (sticky, prefix-aware) routing to the same replica for the same prefix is the fix — an underappreciated, real lever most teams never touch.
