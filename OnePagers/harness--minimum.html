The Minimum Harness

Grow it from failures, not diagrams · harness › minimum

corehigh confidence2026-09-03

Hook

Harness engineering has a failure mode of its own: building orchestration before establishing that the task needs it. More planners and queues mean more failure points and blurrier accountability.

Mental model

Subtraction is a design strategy. One agent, three tools, one workspace, one state record, one verifier, three exits — then every added component must name the observed failure it removes. Pi publishes a "what we did not build" page; copy it.

Decide

Use when the minimalist shape is right
  • Single owner, exploratory work, shell already trusted
  • A small auditable surface matters more than breadth
  • The harness should embed inside someone else's system
Skip when minimalism is the wrong trade
  • You need per-capability authorization and an audit trail
  • Multi-tenant, multi-engineer, mismatched vocabulary
  • Output reaches a customer, so evals are not optional

Aryaka

Choosing a shape for the NetDevOps assistant. Take from Pi: a small typed tool set — find_device, query_telemetry, read_runbook, draft_rca — not bash, because an audit trail that says which capability ran is a requirement here. And take sessions as a forkable tree: diagnosis is exploratory, so an engineer whose hypothesis dead-ends branches from before the mistake instead of continuing with poisoned context.

Take from Hermes: three-pillar memory in plain files, consolidated by a cheap model gated on ticket close. Reject its no-embeddings choice — an engineer types "tunnel keeps dropping" against a runbook saying "IPsec SA renegotiation flap", and keyword-only retrieval returns nothing while looking identical to having no memory.

Assumption: ~30 engineers, ~40 durable facts each. Preferences local per engineer; customer facts shared, because a lesson about a customer must not stay on one laptop.

Say this

My first harness is one agent, three tools, one workspace, one verifier and three exits. Every component after that has to name the observed failure it removes — I'll build the ones with traces behind them.

Trap

Five MCP servers attached, one actually used. The tell: you cannot say what fraction of turns invoke each server, so a 25k–100k token tax per turn is invisible — paid whether the capability is used or not.

Probe

Pi ships four tools and no MCP. What does bash buy, and what does it cost?
Show answer

It buys an unbounded action space at zero context cost — anything reachable from a shell is available without being modelled as a tool. It costs every guarantee a typed interface gives: argument validation, per-tool permissions, and measurable tool-selection accuracy. bash is one line in every trace, so you cannot evaluate whether the agent chose well — there was only one choice.

A harness stores conversations as a tree rather than a list. Why does that matter?
Show answer

Forking from message N is the cleanest possible context reset: keep exactly the prefix that was good, discard the exploration that poisoned it. More precise than compaction and cheaper than a summariser. It is what an engineer actually wants after a dead-end hypothesis — branch from before the mistake, rather than continue polluted or start over.

A product calls itself a self-improving agent. What do you test, and what do you find?
Show answer

Run a hard iterative task, then ask what it saved. Hermes was observed saving a fact ("YouTube scraping quirk") and no skill. Facts are easy — they are stated in the trace. Procedures require recognising that a sequence was worth generalising, which is a harder inference. Also test any scheduled feature by not polling it: a cron that only materialises when asked is not scheduled work.
