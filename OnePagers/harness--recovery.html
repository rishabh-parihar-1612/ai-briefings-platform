Recovery & Exits

Which one ran this month? · harness › recovery

corehigh confidence2026-09-03

Hook

"We retry" is one mechanism offered as four. Recovery is retry, resume, rollback and escalate — and untested recovery is a belief, not a control.

Mental model

An autonomous actor without an enforced stop is an operational risk whatever makes its decisions. So every run needs named exits and four independent ways back — each with a prerequisite, each drilled, because they only run on the bad day.

Decide

Use when the mechanism is earned
  • Any write exists, reversible or not — rollback gets designed
  • Work spans a restart, a deploy, or a human wait
  • Errors arrive with a distinguishable retryable flag
Skip when do not fake it
  • The action has no recorded inverse and nobody will test one
  • Escalation would land in a queue with no owner
  • Retry is a loop with no idempotency guarantee

Aryaka

The diagnosis harness's exits. One write tool: post the diagnosis to the ticket. Retry fires only on errors flagged retryable: true — a vendor API timeout, never a rejected write. Resume reads task state (hypotheses with confidence, tried-and-failed, next safe action) and re-verifies anything time-sensitive, because a tunnel state observed before a 40-minute gap may have moved. Rollback is "delete the posted comment", executed in a monthly drill, not described in a design doc. Escalation goes to a named on-call queue with a response-time expectation.

Human sees: the drafted comment plus the observations it cites, inside a budget of 8 actions and 12 minutes. Breaks when: the kill switch is exercised only between runs — stopping the loop is easy, and what a half-written ticket comment leaves behind is the real question.

Say this

Recovery is four separate mechanisms — retry, resume, rollback, escalate — and I'd ask which of them has actually run this month. An untested rollback is a belief.

Trap

Building one mechanism and reporting four. The tell: "we retry" answers a question about recovery, and nobody can name a rollback that was executed against real state outside a design document.

Probe

Knight Capital was not an AI system. Why is it in a harness deck?
Show answer

Because the failure was autonomy without an enforced stop, not intelligence. ~$440M in about 45 minutes, 1 August 2012, from old code left active on one of eight servers. An autonomous actor that cannot be stopped is an operational risk whatever makes its decisions — which is why the kill switch and the drained-run test are harness requirements, not AI requirements.

Resume works. Why might the resumed run still be confidently wrong?
Show answer

Stale state. An observation captured before the interruption may no longer be true, so the state schema needs timestamps and the resume path needs a re-verification step for anything time-sensitive. Resume is also the least-tested path in any agent system, because it only runs on the bad day — the practice that catches decay is killing a percentage of eval runs mid-flight in CI and asserting the resumed outcome matches the uninterrupted one.

Your approval gate passes 97% of requests in about two seconds each. What now?
Show answer

Treat the control as failed. Above roughly 95% it is approval theatre, and two-second decisions mean unapproved writes with a compliance artifact attached. The fix is narrowing the approval class — approve by exception on an action class with a demonstrated rollback and an escalation-quality number — plus deterministic auto-approve bands so the remainder is rare enough to read.
