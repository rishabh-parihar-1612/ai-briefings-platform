Grounded RAG Under Hard Constraints

LLM is the last step, not the boundary · data-to-ai-engineer › grounded-rag-design

Hook

The LLM is the last step, not the security boundary — and never let a model produce a number that already exists in a table.

Mental model

Route by question type: exact facts come from governed tables with the model only formatting; narrative questions go to chunked documents. Access filtering happens before retrieval, identically enforced in the warehouse and the vector layer.

Decide

Use when
  • Designing a RAG system with a "must not hallucinate" or "must be traceable" hard constraint
  • Different users must see different subsets of the underlying data
  • Corpus scale will grow past what a single vector search can serve affordably
Skip when
  • All facts are narrative/subjective with no exact-value table to protect
  • Every user has identical access to the full corpus
  • Corpus size is small enough that a funnel adds complexity with no measured benefit

Aryaka

Aryaka's NetDevOps assistant maps line for line: "last 3 availability dips for this circuit" is an exact-fact question served from telemetry tables, the model only formatting; "what does the runbook say about SA renegotiation flaps" is narrative, served from chunked runbook sections. An engineer on account A must never retrieve account B's config — identity and scope filter both the telemetry tables and the runbook chunks before the model sees anything, with warehouse ACLs and vector-metadata rules reconciled on a schedule. Every RCA claim must be traceable to a telemetry response or runbook chunk — the same post-generation attribution check as the clinical case, adapted to customer configuration data under NDA.

Say this

Never let a model produce a number that exists in a table. Retrieve it exactly, let the model only format it — semantic retrieval over a chunk returns a similar value, dangerous, not degraded.

Trap

Filtering unauthorized content out after generation instead of before retrieval. The tell: if it entered the model's context, it can shape the answer even with the citation stripped — a summary of a record you can't see is still a disclosure.

Probe

A clinician asks "what were this patient's last three abnormal lab values?" Should this go through vector search?
Show answer

No — this is an exact fact that exists in a table. Chunking and semantically retrieving it can return a value similar to the right one (different date, adjacent patient), which is dangerous, not degraded. Route it to a governed table query; the model only formats the response.

How do you enforce that a neurology doctor can only see neurology patients' records in a RAG system?
Show answer

Filter before retrieval, not after — take identity and scope from the enterprise identity system at login, and filter both the structured tables and the document chunks so the model never sees unauthorized context at all. A system prompt instruction is one injection from failing and leaves no audit trail.

Your RAG system passes all its evals, but you're still worried about hallucination in production. What's missing?
Show answer

Likely the third gate — post-generation attribution checking, verifying every claim in the generated answer is supported by the retrieved context. The first two gates are cheap and common; attribution checking is the one that catches a hallucination already in a fluent answer.
