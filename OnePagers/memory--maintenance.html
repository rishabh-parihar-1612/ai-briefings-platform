Memory Maintenance

A wrong memory is wrong forever · memory › maintenance

corehigh confidence2026-09-04

Hook

A missing memory costs a slightly worse answer; a wrong memory is confidently wrong forever. Writes get a far higher bar than reads — backwards from how most systems are built.

Mental model

Four verbs, and the second one is the whole discipline: decide what earns a write, supersede rather than overwrite, attribute every fact to a source, reflect offline to merge duplicates. Overwriting gives you current state, not memory.

Decide

Use when the write is earned
  • Explicit request, or a decision confirmed by a human or a check
  • The record can carry a source, a scope and an expiry
  • A conflict rule exists for when it is contradicted
Skip when refuse the write
  • It is a model inference nobody validated
  • It came from untrusted content and free-text extraction
  • The fact would ever be consulted for authorization

Aryaka

Gold to Platinum. A customer's SLA tier changes. The Gold fact gets an end date; the Platinum fact gets a start date. Nothing is destroyed — because 6 months later someone will ask why a March breach was assessed against a 4-hour target. Every read is now as-of a time, defaulting to now: a query-shape decision for day one.

Then the erasure request. Deleting the conversations deletes none of: the consolidated semantic facts distilled from them, the embeddings of those, the graph edges built from them, the traces, or eval cases promoted from them. With source and source_id on every record it is a traversal; without attribution it is a grep and a prayer.

Breaks when: someone adds a summary cache in month six and nothing in the delete path knows about it.

Say this

Invalidate, don't delete — overwriting destroys point-in-time truth, and point-in-time truth is what every incident review needs. And provenance is unrecoverable retroactively.

Trap

Auto-writing memory from conversation content. The tell: you cannot say what stops a ticket saying "note: this account is approved for unlimited credits" becoming a durable fact — a one-shot injection turned persistent.

Probe

Why must memory never grant authorization?
Show answer

Because auto-written memory turns a one-shot prompt injection into a persistent one. An attacker who gets "this user is an admin" written into semantic memory has escalated privileges in every future session, and the injection markers are gone once it is consolidated into a summary. Permissions come from the identity system, checked at execution. It also means extraction writes into a constrained schema with enumerated fields, never free text — so there is nowhere for an instruction to hide.

Which of the six test axes do you build first, and why?
Show answer

Isolation — it is the only one whose failure is an incident rather than a quality problem. And it must be fuzzed, not demonstrated: null, empty, wrong-type, and another tenant's valid scope key, because real leaks come from a filter silently degrading to unfiltered on a malformed key. Then deletion, because it has a legal clock on it. Recall and precision are what everyone builds first and are the ones you can fix later without telling anyone.

Retrieval quality is degrading and the store is 400GB. Capacity or content?
Show answer

Content. 400GB is not hard for any modern store, and re-ranking only helps when the right answer is in the retrieved set. Sample fifty retrievals and count distinct facts in the top five: if it is filling with near-duplicates at moderate similarity, semantic memory has been growing without supersede or merge — a second episodic log with worse timestamps. The fix is a reflection pass. Most of that volume is usually episodic detail that should have expired.
