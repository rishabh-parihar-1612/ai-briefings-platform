Durable Execution, Aggregate Auth, HITL

State, side effects, and rate are different · deep-agents › production-concerns

supportinghigh confidence2026-09-10

Hook

Standard infrastructure gives you none of the four things a long-running agent actually needs: durable execution, memory, aggregate authorization, human-in-the-loop as a primitive.

Mental model

Durable execution solves state, not side effects. Authorization needs rate and pattern, not just a per-call predicate. Human-in-the-loop is four co-equal primitives, not an approval checkbox.

Decide

Use when
  • A task can run long enough to fail partway through
  • Any tool call has an externally-visible, hard-to-reverse effect
  • More than one human-facing checkpoint (interact/interrupt/approve/stream) is needed
Skip when
  • Every task completes in one or two steps — nothing to checkpoint
  • All actions are read-only — no side-effect ledger is needed yet
  • Tool count is genuinely small and untested — measure before adding a router

Aryaka

Aryaka's network-analysis agent checkpoints per site processed; a failure at site 340 of 800 resumes at 340, not 1. The side-effect ledger is free by design here: the agent only ever drafts outreach emails, never sends them — sending is a separate, human-approved action, so replay can never double-send anything. A middleware budget caps analysis at N sites per run so a malformed query can't turn into a telemetry stampede across the full customer base, and progress streams per site so a NOC lead watching an 800-site run never mistakes a slow pass for a hung one.

Say this

Durable execution is a state problem and a side-effect problem — checkpointing only solves the first. Design side effects out (draft, don't send) before building a ledger to track them.

Trap

Treating checkpoint-and-resume as sufficient for a long-running, write-capable agent. The tell: resuming at step 66 after step 40 sent an email either re-sends it or needs a recorded fact that it already happened — checkpointing alone answers neither.

Probe

Your agent fails at step 67 of a 123-step task. What actually happens on restart, and what's the hidden risk?
Show answer

Checkpointing resumes at step 66, not step 1 — but only safe if steps 1–65 were idempotent or externalized. If step 40 sent an email, resuming either re-sends it or needs a recorded fact that it already happened; checkpointing solves the state problem, not the side-effect problem.

How should an agent be authorized to send emails on a user's behalf?
Show answer

A per-call OAuth scope is the floor, not the answer — it authorizes one email and a thousand identically. The practical fix is budget-based authorization (a quota per scope per session) enforced in middleware, escalating to a human on overage rather than failing silently.

Your agent has 50 tools. Should you add a routing layer?
Show answer

Not by default — measure first-tool-choice accuracy on real traces first. A production system serving major customers runs ~50 flat tools successfully; "10 tools needs a router" is folklore, and a router fixes none of the three real failure modes (description, granularity, bad arguments).
