Loop Engineering

Continuing is a decision · agent-loop

corehigh confidence2026-09-03

Hook

A cron job that asks a model to try again is repetition. In a loop, continuing is a decision requiring evidence — a new observation, not a new attempt.

Mental model

Given that you chose a loop, five elements make it safe: trigger and goal — the prohibition is half the goal — working state, typed observations, verification, budgets and exits. Termination is checked before anything is spent.

Decide

Use when a loop is the right shape

Skip when a workflow belongs there

  • The trace shows the same tool sequence every run
  • Only one or two steps are actually uncertain

Aryaka

Failed-deployment investigation. Trigger: a post-change health check fails on a customer edge device. Goal: an evidence-backed diagnosis or a safe handoff. Prohibition: no config change, no restart, no customer-visible message — enforced by permissions, not stated in the prompt.

System: seven read-only sources — change log, telemetry, tunnel state, link health, config store, similar cases, ticket history — each returning a typed result with a retryable flag. The diagnosis must cite observations, and every citation must resolve to a real record or the harness rejects the answer before it reaches a human. Budgets: 8 actions or 12 minutes; 3 runs per change ID, keyed on device + alarm class + window.

Human sees: one of the four exits, with a five-field handoff. Assumption: ~200K input tokens ≈ $0.60 a run, so a pathological change caps near $1.80.

Say this

Continuing is a decision that requires evidence — two cycles with no new observation is an exit condition, not a retry. And "finished" has to be a verified exit, never a declared one.

Trap

max_steps offered as the whole safety story. The tell: budget-exhausted runs aren't tagged progressing versus spinning, so the cap only ever ratchets upward — the failed runs are visible and the money saved is not.

Probe

Overnight it burned $400 and produced nothing. What is your first question?
Show answer

One long run, or many short runs of the same task? Two different incidents hide behind one number, and it is usually the second — a deterministically failing task retried by whatever triggers it, each run bounded and cheap, the aggregate unbounded. Per-run caps are structurally blind to that. Fix: a task-identity rule (same device + alarm class + window = one task), a per-task attempt budget, and spend-rate alerting across all runs.

The agent reported it fixed the issue. It didn't. Whose bug?
Show answer

The loop's exit condition, not the model's. The run was allowed to end successful on the model's own say-so, and no instruction fixes that — a fluent system always produces a convincing completion sentence. Make "finished" verified: the output contract requires citations and the harness checks each resolves before the answer leaves. Where no deterministic check exists, prefer the insufficient-evidence exit over a confident answer.

Insufficient-evidence has fallen to near zero, escalation rate is flat. Win or regression?
Show answer

Regression. The honest exit is socially unpopular — users read it as the agent failing, support reads it as noise — so within a quarter someone lowers the evidence bar, and confident wrong answers replace honest non-answers while the metric improves. Report the two exits together. What makes the honest exit survive politically is handoff quality: ruled-out hypotheses and timestamped observations, so the human doesn't start from zero.

Loop vs Graph

Never put understanding in a node · agent-loop › loop-vs-graph

corehigh confidence2026-09-03

Hook

A loop discovers what to do next. A graph is when you know the shape and want the parts to move together. They are not alternatives — they coexist and nest.

Mental model

The ladder — prompt, context, skills, loop, graph — is a pendulum between I decide and you decide, not a maturity climb: rung five reintroduces rung three's constraint, because a graph is a procedure you had to know in advance.

Aryaka

Morning operations brief, 07:00 weekdays. A scheduled trigger fans out to four concurrent fetches — overnight flap incidents, change requests awaiting my review, carrier advisories, last shift's handover notes — then one synthesis. Both tests pass: the set hasn't changed in months, and no node performs understanding.

Where the loop lives: inside flap_incidents. Why it flapped is open-ended — the peer, the underlay, an overlapping change window, an advisory. Order depends on findings: a loop, correctly, as a leaf node.

Human sees: a cheap router labels each flap routine or needs-investigation, and recall on needs-investigation is tracked — a missed investigation is the expensive error. Breaks when: a carrier-wide outage fans out into hundreds of investigations at 07:00, so the guard caps calls per incident and returns "widespread event, N sites affected, investigation suppressed."

Say this

They nest — a graph for the known shape, loops as leaf nodes. Consolidate when the workflow stops changing, and never put understanding in a graph node; put fetching there.

Trap

"Support has SOPs, so build the graph." The tell: your first node is an intent classifier — understanding in a node, exactly the class frontier models delete — and the taxonomy has changed twice this quarter.

Probe

One team migrates loops to graphs. Another deleted its graph for a loop and quadrupled retention. Who's right?
Show answer

Both — the deciding variable is what the nodes did. Harmonic's nodes performed understanding (parse semantics, extract location, extract funding stage), compensating for a model limitation that expired; that class should be deleted the moment it can be. The advocate's nodes fetch known things, which is just concurrency and stays correct. Test per node: would a better model make this unnecessary? Every yes belongs in a loop. And audit the rest of your model-compensating structure on every upgrade — few-shot scaffolding, intent classifiers, output-repair passes.

This agent takes 30 seconds. What do you attack first?
Show answer

The structure, not the model tier — a loop is serial by construction. Four calls at ~2s behind four model decisions is 20–30s; fanned out it is max-branch plus synthesis, 6–8s, at a third of the model calls. Then check the system prompt for "call all four of these tools" — that is a graph written in English with none of the concurrency. Operator caveat: profile first, because it is often one uncapped tool response, and optimise p95 rather than the mean.

"Agent graphs are just Airflow with extra steps." Answer it.
Show answer

Substantially right, and say so first — Airflow 2015, Step Functions 2016, and the engineering discipline transfers. Three things are new, each a new eval requirement: non-deterministic nodes (measure per-node output quality, not success), model-picked edges (measure routing accuracy per branch), guards (measure trigger rate and false positives). The engineering discipline transfers; the testing discipline doesn't. Then use it as a test: strip the LLM nodes and model-chosen edges, and if Step Functions does the rest better, use Step Functions.

The Agent System Stack

Six layers, one symptom-to-layer map · agent-stack

supportinghigh confidence2026-09-10

Hook

"The agent is unreliable" isn't a bug report — it's five different bugs hiding in one sentence, and each lives in a different layer of six.

Mental model

A model reasons; an agent is the system that gives that reasoning a world to act in, a boundary it cannot cross, and evidence the outcome happened. The stack is a debugging tool, not a taxonomy.

PromptContextTools+MemoryHarnessLoopEval

Decide

Use when invest in the full stack
  • Task needs more than one model call or touches more than one document
  • Any write action reaches a real system of record
  • Debugging "it's unreliable" reports already wastes real time

  • A single model call in a known format solves it
  • Steps and order are fully known in advance — use a workflow
  • No production trace has justified going past layer two yet

Aryaka

Aryaka's network-diagnosis agent maps onto all six layers: prompt (evidence-backed diagnosis, schema-validated), context (filter-then-rank over historical cases, never the whole corpus), tools (seven read-only sources, one approval-routed write), harness (read-scoped identity, one kill switch), loop (8 actions or 12 minutes, four exits), eval (~200 frozen tickets, deterministic grader, five trials). When a NOC engineer reports "the diagnosis was wrong," the first move isn't a prompt edit — it's pulling the trace and classifying it into one of the six symptom buckets, because "wrong" from stale context and "wrong" from a bad tool argument get fixed in completely different places.

Say this

"Unreliable" isn't a bug report. Give me a trace and I'll give you a layer — six of them, and each symptom maps to exactly one.

Trap

Answering an architecture question with a framework name and a box diagram instead of six responsibilities. The tell: every follow-up — what can it touch, when does it stop — has nowhere to attach in that diagram.

Probe

A user reports "the agent is unreliable." What's your first move?
Show answer

Refuse the word — pull 20 failed traces and classify each into one of six layers. The distribution is usually lopsided and almost never the layer the team assumed; only then pick a fix.

Two tools, get_device_status and get_device_config, both described as "returns device information." What's actually broken?
Show answer

Nothing throws an error — the agent silently picks whichever description reads as more relevant, and quality degrades with no visible failure. Overlapping tool descriptions are a contract bug, not a model limitation.

When does an agent legitimately need memory added?
Show answer

When tasks genuinely span sessions — not because the demo would feel nicer — and only once you can name who corrects a wrong memory. Without a corrector, engineers become the correction path via manual database edits.

Aryaka

An Aryaka NetOps triage agent built open-source: Ollama for early iteration, moving to vLLM only once support-team concurrency actually requires it. LiteLLM sits in front from day one so a model swap is a config change, not a rewrite. The tool layer runs sandboxed with least-privilege, read-only credentials against production monitoring, scoped to the harness's own permission-boundary design rather than trusted by default.

Say this

Self-hosting isn't a cost-avoidance move, it's a cost-shape change — and the first ops responsibility it hands you is auth on every store a managed vendor used to default on.

Trap

Treating "open-source" as synonymous with "free and safe by default." The tell: a self-hosted vector database reachable from the public internet with no auth configured — the gap found in ~12,800 real, scanned instances.

Probe

A team wants to self-host their entire AI stack to save on API costs. What's missing from that pitch?
Show answer

The ops cost isn't zero — GPU time, storage, and specifically the engineering hours to configure auth correctly on every self-hosted store are real costs a managed vendor's defaults used to absorb silently.

What's the actual difference between Ollama and vLLM, if not "dev vs. prod"?
Show answer

Two different jobs: Ollama gets one developer running a model quickly; vLLM keeps expensive accelerators busy under real concurrent load. A low-concurrency "production" workload can correctly run on Ollama; reaching for vLLM by reflex wastes setup time for no throughput gain.

Why do self-hosted vector databases keep getting breached when every major one supports authentication?
Show answer

The software isn't the failure — the deployment discipline is. ~12,800+ instances were found publicly exposed with zero auth via routine scanning; self-hosting hands you the ops responsibility a managed vendor used to default on, and skipping it is the actual gap.

Arithmetic-First System Design

Aryaka's NetOps support desk: hundreds of engineers, not millions of consumers — an immediate signal this is a different scale problem than a consumer bank chatbot. Trap

Opening a system-design answer by naming a vector database, a reranker, and an agent framework in one breath. The tell: no number ran yet, so every component is a taste claim, and the interviewer can only counter with taste.

Probe

You're asked to design an assistant with a $0.02-per-conversation target. Your routing split brings cost to $6,000/day across 200,000 conversations. Is that under budget?
Show answer

No — $6,000 ÷ 200,000 = $0.03/conversation, 50% over budget. The naive read conflates the conversation count with the higher request count used earlier in the token arithmetic; catching that division error yourself, out loud, is the stronger signal.

A stakeholder proposes fine-tuning weekly since "policies change weekly." What's wrong with that plan?
Show answer

Fine-tuning updates style/behavior, not reliably-recallable facts, on a days-to-weeks retraining cycle — a fine-tuned model chasing weekly changes is perpetually one cycle stale. RAG's reindexing cycle can actually match that frequency; fine-tuning's retraining cycle can't.

RAG answers have degraded in production. What do you check first?
Show answer

Top-down through the funnel, never the prompt first: is the index stale? Are the top-50 candidates actually relevant? Is the reranker improving on that set, or is chunking feeding it garbage? Only once all three are clean does the prompt or model become a plausible suspect.

Aryaka

Aryaka's NetDevOps team lets engineers ask a coding agent to write and ship small automation scripts — config-drift checks, tunnel-health remediation — against the SD-WAN orchestration API's staging tier, in a disposable sandbox torn down after each run. Review is waived for staging-only and internal-tooling scripts, where rollback is a redeploy under a minute; it stays mandatory for anything reaching the production config-push path, because a bad push touches a customer's live network state, not an internal dashboard. Agent-run tests are the fast first pass inside the sandbox; a separate CI stage still gates production because "exhaustive" hasn't been measured for this codebase yet. Modeled cost: 15 tasks/day × 20 min × ~$0.15/hr ≈ $0.75/day in sandbox compute — trivial next to the real cap, the human-approval queue.

Say this

It's not "we trust the agent so we skip review" — it's mean-time-to-recovery over mean-time-between-failures, and it only holds where rollback is fast, tested, and the blast radius stays internal.

Trap

Waiving review or CI by authorship ("AI wrote it") instead of blast radius. The tell: nobody can name the measured MTTR or point to a rollback that has actually fired — only one that was described in a design doc.

Probe

Your team waives code review for agent-authored changes. What's the first question a good interviewer asks back?
Show answer

What's the blast-radius line — and has the rollback for that category actually executed once against real state, or only been described? MTTR-over-MTBF only holds if detection and rollback are proven, not assumed; Amp's own migration only counts because the rollback path fired for real on a live production change, not in a design doc.

Someone says "why do you even need CI if the agent runs its own tests?" What's the sharpest honest answer?
Show answer

CI's job was never "catch what a human missed" — it's the deterministic, exhaustive stage that runs regardless of what fit in anyone's context window, human or agent's. Quinn Slack's own objection to himself: "you don't trust the agent to be exhaustive" — it runs what's in its context, not necessarily everything the project needs.

A coding agent runs in a cloud sandbox with a token scoped to read-only production logs. Is that safer than a developer's laptop?
Show answer

Only if the token is scoped by resource AND time. A read-only token that never expires is still a live standing risk months later — the same as an unrevoked laptop credential. Amp's OIDC tokens expire (e.g. 30 minutes) whether or not the task finished, forcing re-authorization rather than assuming safety from "read-only" alone.

Aryaka

Say this

The comparison that matters isn't "sandbox vs. no sandbox" — it's what the credential can reach and for how long. Scope by resource and time, or you've just relocated the laptop's blast radius.

Trap

Treating "read-only" as the whole safety argument. The tell: nobody can say when the token expires, only what it can reach — a read-only grant with no expiry is still a live risk months after its task is forgotten.

Probe

Your agent's credential is read-only and scoped to one database. Is that sufficient?
Show answer

A task's OIDC token expires before the task finishes. What should happen?
Show answer

The task re-requests a fresh token through the same approval gate, or hands off to a human — the expiry is a forcing function for re-authorization, not an outage. A task that silently needs standing access for hours is a sign it was scoped wrong, not a sign the expiry was too short.

How does this credential model differ from the rate/aggregate quotas covered under deep-agents?
Show answer

They're separate axes that both matter. Rate/aggregate caps the volume of an action within a session ("one email is fine, a thousand is an incident"); time-boxing caps the window in which any access exists at all, regardless of how much was done inside it. Neither substitutes for the other.

Say this

Context is a budget, and the unit of design is the next decision. Three buckets: useful now, useful later — that's retrieval — and harmful now, which most teams don't have at all.

Trap

Fixing every incident by adding to the prompt. The tell: no prompt block carries a date or an owner, so after six months the window is a museum of past incidents and removing any one of them is unfalsifiable risk.

Probe

You have a 200K window. Why not put everything in?
Show answer

The agent contradicted itself between turn 4 and turn 12. Diagnosis?
Show answer

Show answer

It is a composite. A good answer can come from bad retrieval — the model knew anyway — and a bad answer from perfect retrieval, so the number cannot separate them and tuning becomes guesswork. Retrieval needs its own metric: recall@k on a labelled set. The labelled set is the project, not the metric: build inter-rater agreement first or you are measuring taste. Then re-measure on corpus growth, because plausible-but-wrong neighbours grow faster than the right ones.

Aryaka

The TAC case-state object. case_id, customer_impact.severity: P1, symptom, confirmed, ruled_out, hypotheses with confidence, actions_taken with results, blocked_actions with reasons, next_action, evidence refs.

The two load-bearing fields. ruled_out is negative knowledge — without it the agent re-suspects the customer LAN after the next compaction. blocked_actions with a reason is what stops compaction quietly making "production configuration change" look permitted.

Breaks when: the agent tests a tunnel restart, gets no improvement, moves to ISP path analysis, compacts to "investigated packet loss" — then re-suspects the tunnel and restarts it a second time in front of the customer. Say this

History is evidence, state is what the agent needs to continue, and context is only what the model currently sees. The context window is not our application's state model.

Trap

Trusting compaction because it is "just summarisation." The tell: you have no pre/post state diff — so a low-confidence hypothesis becoming a stated fact is invisible, and the wrong answer arrives three turns later with nothing in monitoring firing.

Probe

Why compact at 60–70% rather than at the limit?
Show answer

Because compaction is itself a model call needing input tokens, output tokens, instructions, the schema and safety margin. At 95–100% you need compaction and cannot afford it — a hard failure, on exactly the longest and most valuable runs. State the rule as headroom, not a number: compact when the remaining task horizon plus compaction overhead plus a margin no longer fits comfortably. Size it from the p95 of tool output, because one uncapped query is ~40K tokens.

How do you know a compaction was correct?
Show answer

Not by text similarity — a correct state can be worded completely differently, and a similar one can have dropped a hard constraint. Evaluate it behaviourally: does an agent working only from the compacted state choose the same next action it would have chosen with the original context? Mechanically, diff the state fields across the boundary and alarm when a confidence value rises with no new observation, or when tried-and-failed shrinks. Then a recovery path: validate, retry with a stronger compactor, fall back to the previous state version.

"Failed before" — so never retry?
Show answer

No, and treating it that way trades a repeat-work failure for a stuck-agent failure. Sometimes an approach failed because conditions have since changed, so record why it failed and under what conditions a retry is valid — retry_allowed with a reason. Operators add the field the schema usually misses entirely: actions already performed, with idempotency keys. Tried-and-failed does not cover tried-and-succeeded, and a resumed run repeating a completed write is the incident the whole schema exists to prevent.

Probe

Why do output tokens cost 3–5× input tokens across nearly every provider?
Show answer

Prefill (processing the prompt) is parallel and compute-bound; decode (generating output) is serial, one token at a time, and memory-bandwidth-bound. Decode genuinely costs more to serve — it isn't arbitrary pricing, and it's why capping output length is the single best latency lever.

Show answer

100% of prompt-cache hits, because caching is an exact prefix match and the timestamp sits at position zero — every request after it invalidates the cache. The system still works, so nobody notices; it just costs 5–10× more than it should until someone checks the hit rate.

Show answer

Roughly ~12%, versus ~95% achievable, because each replica only caches what it happens to see. Cache-aware (sticky, prefix-aware) routing to the same replica for the same prefix is the fix — an underappreciated, real lever most teams never touch.

You believe retrieval caused a wrong answer. How do you prove it rather than assert it?
Show answer

Counterfactual attribution — substitute the retrieval step's output with a known-good value and re-run the rest unchanged. If the answer becomes correct, retrieval is a strong causal suspect; if it doesn't, retrieval was never the cause, and that negative result is worth as much as a positive one.

Show answer

Durable execution is a state problem and a side-effect problem — checkpointing only solves the first. Design side effects out (draft, don't send) before building a ledger to track them.

Trap

Treating checkpoint-and-resume as sufficient for a long-running, write-capable agent. The tell: resuming at step 66 after step 40 sent an email either re-sends it or needs a recorded fact that it already happened — checkpointing alone answers neither.

Probe

Your agent fails at step 67 of a 123-step task. What actually happens on restart, and what's the hidden risk?
Show answer

Checkpointing resumes at step 66, not step 1 — but only safe if steps 1–65 were idempotent or externalized. If step 40 sent an email, resuming either re-sends it or needs a recorded fact that it already happened; checkpointing solves the state problem, not the side-effect problem.

How should an agent be authorized to send emails on a user's behalf?
Show answer

A per-call OAuth scope is the floor, not the answer — it authorizes one email and a thousand identically. The practical fix is budget-based authorization (a quota per scope per session) enforced in middleware, escalating to a human on overage rather than failing silently.

Your agent has 50 tools. Should you add a routing layer?
Show answer

Not by default — measure first-tool-choice accuracy on real traces first. A production system serving major customers runs ~50 flat tools successfully; "10 tools needs a router" is folklore, and a router fixes none of the three real failure modes (description, granularity, bad arguments).

  • The consequence class of a wrong action is above "advisory"
Skip when lighter controls suffice
  • The path is fully read-only against a trusted, scoped corpus
  • Output never reaches a customer or a downstream system of record
  • No tool call in scope can mutate anything

Aryaka

The NetDevOps support assistant's output guardrail is the Air Canada control: it must not state an SLA credit or maintenance-window policy it can't ground in the current runbook, and refuses rather than generates when grounding fails. Its action guardrail sits in front of push_config, not in the prompt — at 10,000 requests/day a 2% output-guard false-positive rate would still block 200 legitimate answers/day, so the false-positive log gets a weekly review and the operating point is tuned per action class: high recall on push_config, high precision on advisory answers.

Say this

I'd separate guardrails from authorization. Content guardrails are probabilistic and fail some percentage of the time; anything where failure is unacceptable goes in a deterministic policy layer, never in a guardrail model alone.

Trap

Saying "we'd add guardrails" and stopping. The tell: no placement is named, no cost tier is chosen, and nobody can say what a 2% false-positive rate costs at your actual request volume.

Probe

Which of the three guardrail placements is the only one that's load-bearing for safety, and why?
Show answer

Action guardrails — deterministic authorization in front of a tool call. Input and output guardrails are probabilistic content controls that reduce the probability of a bad outcome; action guardrails reduce the possibility of one, because they sit between the model's proposal and the irreversible effect.

A guardrail service goes down mid-incident. What's the correct fail-open/fail-closed split, decided before the incident?
Show answer

Read-only and advisory paths fail open, logging loudly and alerting — availability wins there. Any write, external communication, or customer-visible output fails closed and degrades to human handoff. Deciding this ahead of time matters because under pressure someone will decide it wrong.

Your output guardrail runs at a 2% false-positive rate on 1M requests/month. What does that actually cost?
Show answer

20,000 legitimate requests blocked — in a support context, 20,000 frustrated customers. That number is why FPR needs an owner and a weekly review of the false-positive log, not a one-time tuning pass at launch.

System: normalize, retrieve the SOP branch (not all 50 pages), filter 10M cases to product=SD-WAN + subtype=Tunnel Flap + region=APAC, down the funnel to 20, compress to evidence records carrying root cause and resolution, then collect live device state. Hypotheses carry supporting and contradictory evidence, so the agent cannot converge on whatever it thought first.

Human sees: a recommendation behind a policy gate, or one of the 6 termination states. Breaks when: the product field has 40 spellings — metadata hygiene sinks these projects, not the ranker.

Say this

Derived indexes are for discovery; systems of record are for truth. The LLM decides what information is needed; deterministic infrastructure decides how to fetch it efficiently.

Trap

"Vectorize Salesforce and forget the source." The tell: you cannot say how a record deleted or access-revoked upstream stops being retrievable — inserts and updates any sync handles, and a revoked record that stays searchable is a compliance incident.

Probe

Live API or vector index for the case history?
Show answer

False binary. Live-only gives latency, API load, token cost and — the one that kills the product — unpredictable execution time. Index-only gives stale truth, sync complexity, hard invalidation, duplicate authority and permission drift. The resolution: the projection serves discovery, a live call serves authoritative verification, and freshness is decided per evidence type rather than once for the system. Publish a staleness SLO and keep a full-rebuild backstop.

Cases contain long email threads. Why not just embed the comment field?
Show answer

It flattens a timeline with authorship. An early customer claim ("we think it's the firewall") and the closing confirmed finding ("ISP packet loss") become indistinguishable after chunking, so the agent retrieves the disproven one and sounds certain. Keep author_type and thread_position on every chunk. And half the bytes are quoted reply chains, signatures and disclaimers — a naive parser attributes quoted text to the wrong author, inverting the exact signal you built.

What actually deserves promotion to durable memory?
Show answer

A much shorter list than people expect, and the shortness is the feature: explicit preferences, explicit instructions, confirmed recurring behaviour, validated troubleshooting invariants, and operational knowledge no system of record owns. Not "customer had packet loss on May 14" — Salesforce and telemetry own that. Everything during a run is workflow state and evidence, with the lifetime of the investigation. Promote only after validation, with provenance and expires_at.

Aryaka

Gold to Platinum. A customer's SLA tier changes. The Gold fact gets an end date; the Platinum fact gets a start date. Nothing is destroyed — because 6 months later someone will ask why a March breach was assessed against a 4-hour target. Every read is now as-of a time, defaulting to now: a query-shape decision for day one.

Trap

Probe

Why must memory never grant authorization?
Show answer

Because auto-written memory turns a one-shot prompt injection into a persistent one. An attacker who gets "this user is an admin" written into semantic memory has escalated privileges in every future session, and the injection markers are gone once it is consolidated into a summary. Permissions come from the identity system, checked at execution. It also means extraction writes into a constrained schema with enumerated fields, never free text — so there is nowhere for an instruction to hide.

Which of the six test axes do you build first, and why?
Show answer

Isolation — it is the only one whose failure is an incident rather than a quality problem. And it must be fuzzed, not demonstrated: null, empty, wrong-type, and another tenant's valid scope key, because real leaks come from a filter silently degrading to unfiltered on a malformed key. Then deletion, because it has a legal clock on it. Recall and precision are what everyone builds first and are the ones you can fix later without telling anyone.

Show answer

Content. 400GB is not hard for any modern store, and re-ranking only helps when the right answer is in the retrieved set. Sample fifty retrievals and count distinct facts in the top five: if it is filling with near-duplicates at moderate similarity, semantic memory has been growing without supersede or merge — a second episodic log with worse timestamps. The fix is a reflection pass. Most of that volume is usually episodic detail that should have expired.

The lexical failure, concretely. A customer writes "the tunnel keeps dropping." The stored memory says "IPsec SA renegotiation flap." Zero token overlap. The keyword path returns empty, and the agent reports it has no record — while the fact is sitting in the store.

Probe

What is the single argument for graph memory, and what does it cost?
Show answer

The edge is the fact. In a graph built from a conversation, an edge labelled "revealed ending of" connects Tom Holland to his next film — two flat facts ("Tom Holland exists", "a film exists") mean nothing. The cost is on write: building nodes, edges and validity intervals is model work per fact, on ingest, which is why one product never finished seeding. Async write path, and recall evals — a graph visualisation is persuasive and its failures are pretty.

Why is a no-memory control group the first thing you build in a memory benchmark?
Show answer

Without it you cannot separate "the memory retrieved the fact" from "the model guessed plausibly." In the race done properly, the control correctly answered "I have no record of that" every time — which is exactly the behaviour you need to distinguish from. Then make the fixture adversarial: an entity plus an event, a fact superseded mid-run, a relationship question, and a query in a different surface form from the stored memory.

Where do mutable facts belong, and why not in embeddings?
Show answer

In structured rows, with the vector index over descriptions rather than over the facts. The deciding constraint is update and delete semantics, not recall quality: correcting an embedded fact means finding and re-embedding every derived chunk, while a structured row is one UPDATE. Teams that put plan tier, contacts or topology into embeddings discover this on the first correction.

Aryaka

A NOC triage agent for Aryaka's SD-WAN/SASE estate: dedupe/enrich by rule (kills 60–80% of alert volume for free), a small model classifies severity, a capped investigation sub-loop (max 8 tool calls, $0.40, 45s) gathers read-only evidence, then one frontier call proposes a root-cause hypothesis with confidence. Shipping a six-agent decomposition because the org chart has six teams. The tell: if you can draw the system as a straight line, it isn't multi-agent — it's a pipeline you made expensive, and you're paying ~15× tokens for the privilege.

Concurrency & Parallelism

IO-bound gets the loop, CPU-bound gets the pool · system-design › concurrency

coremixed confidence2026-09-13

Hook

"Parallelize tool calls" is IO-bound advice — it doesn't transfer to a CPU-bound step in the same agent loop, and that gap is where a working system stalls.

Mental model

Classify the step first: does it wait on something external, or compute continuously once started? IO-bound gets a cheap event loop; CPU-bound gets real execution units. Mixing them on one lane is the failure.

Classify IO vs CPU-boundIO-boundevent loopCPU-boundprocess poolNever mix on one loop

  • No CPU-bound step exists anywhere in the loop yet

Aryaka

The NOC triage agent runs two different jobs: sweeping every active tunnel for telemetry (waits on each edge device's API — IO-bound) and, once a batch flags an anomaly, correlating logs for root cause (continuous computation once started — CPU-bound). The sweep runs on one async event loop: thousands of tunnels in flight at once for tens of megabytes of overhead total (Assumption). The root-cause pass runs on a worker-process pool sized to physical cores, never inline on the sweep's loop. Assumption: a 300-tunnel anomaly burst at ~2s CPU time each finishes in ~44s on a 14-worker pool versus 300s serial — the split that keeps one bad batch from stalling telemetry for every other customer sharing the box.

Say this

An event loop and a process pool aren't competing answers — they answer different questions. IO-bound gets the loop, CPU-bound gets the pool, and "parallelize tool calls" was only ever describing the first half.

Trap

Reusing the IO-bound concurrency the parent card recommends for a new CPU-bound step — local reranking, embedding, log parsing. The tell: unrelated requests stall the moment that feature runs, because it never yields control back to the loop.

Probe

The parent card says "parallelize independent tool calls." A teammate applies that to a new local-reranking step and it makes things worse. What did they miss?
Show answer

That advice is IO-bound advice — it assumes each parallel unit spends its time waiting, not computing. Reranking is CPU-bound: it never yields, so running it on the same event loop stalls every other request sharing that loop instead of speeding anything up.

Your team adds threads to a CPU-bound Python step and throughput doesn't move. What's wrong, and what fixes it?
Show answer

Python's GIL lets only one thread execute bytecode at a time per interpreter, so threads add scheduling overhead with zero parallel gain on CPU-bound work — one directional measured run showed 24 threads at the same wall-clock time as one thread (~2.3s). The fix is a worker-process pool, one process per physical core, since each process owns its own interpreter and GIL.

A capacity requirement says "support 10,000 connections." What's the sharper question before you design anything?
Show answer

Whether those 10,000 are idle/waiting or actively computing — the number that breaks a system is rarely the biggest one in the requirements. Ten thousand IO-bound connections need one cheap event loop; a hundred CPU-bound ones can stall a system built only for the first case.

Aryaka

An SD-WAN incident-triage agent's context grew over six months: 50 syslog lines became 200, then the full device config, then 10 tickets, then the SLA document. Cost per triage rose from $0.04 to $0.71, p95 latency from 4s to 38s, and accuracy on the original test set dropped, because the signal was buried in 60,000 mostly-irrelevant tokens. The fix was a context-assembly function keyed on step and state: always the structured alert summary; on root-cause, top-3 reranked runbook sections plus a config diff since last known-good, never the full config; never the SLA document at all — a tool looks up the one field needed. Cost returned to $0.06, latency to 6s, accuracy above the original baseline.

Say this

Retrieval beats accumulation, and structured summaries beat raw dumps. Cost per successful task is the one number that captures quality and economics together — the number an executive actually understands.

Trap

Optimizing prompt wording to save tokens while every step still runs on one frontier model. The tell: the bill doesn't move — routing is a 5–20× lever, prompt trimming a few percent, so you're polishing the smallest number on the page.

Probe

Your monthly model bill triples with no corresponding traffic increase. First thing to check?
Show answer

Cost of failed runs — retries, abandoned workflows, and timeouts routinely consume 20–40% of spend in immature systems and produce nothing. Check for a task-identity rule catching runaway retries of one failing task before assuming traffic grew.

You have a stable 3,000-token system prompt and unchanged tool definitions for months. What cost lever have you likely left on the table?
Show answer

Prompt caching — 50–90% off input token cost when the prefix is stable. It requires ordering stable content first and variable content last; any harness that rewrites earlier messages destroys its own cache.

A colleague proposes optimizing latency by "using a cheaper model everywhere." What's the sharper question?
Show answer

Which of the 9–12 calls per turn are T0 (no model needed at all) versus genuinely T3 judgment. Eliminating a call is a 100% win; downgrading a model class that still needs judgment just moves the failure from cost to accuracy.

Agentic Security — The Threat Model

Injection is privilege escalation, not bad text · system-design › security

Hook

The model is in the control path, so a successful injection doesn't produce bad text — it produces actions taken with your credentials.

Mental model

Every input reaching the model is attacker-controlled until proven otherwise; every output is untrusted until validated. Least privilege is the one control that can't be talked out of.

Aryaka

Aryaka's NOC triage agent reads syslog and ticket text — both attacker-influenceable, since customers write directly into tickets. That content is delimited as DATA, never instructions. The agent's credential is read-only against the controller API and structurally cannot reach the config-push API in v1 — the worst-case-if-compromised answer is "reads more logs than it should," not "pushes a bad config." Model output is never interpolated into a CLI command. The dual-channel triad is broken deliberately: this agent reads untrusted content but holds no external send capability at all. When remediation lands in v2, push_config becomes DESTRUCTIVE: approval, dry-run diff, commit-confirm with a 120-second auto-rollback.

Say this

Least privilege is the only control that can't be talked out of. If the agent were fully compromised right now, what's the worst it could do — and is that answer acceptable?

Trap

Defending only the input side: sanitizing messages, a guardrail model, a prompt instruction not to follow retrieved text. The tell: indirect injection never touches the user's message — it arrives inside a ticket, a webpage, or a log line read later.

Probe

Your agent reads support tickets, has access to the customer database, and can send email. What's the first architectural question?
Show answer

Which leg of the dual-channel triad to break — reads untrusted content + holds private data + external send capability is a complete exfiltration path. Remove send capability from this agent, or remove its access to untrusted ticket text, before anything else.

A third-party MCP server exposes 40 tools to your agent. What's the risk MCP itself doesn't solve?
Show answer

MCP standardizes the interface, not the security model. The permission boundary is whatever credential the server runs with — an admin token means every connected agent has admin — and the server's tool descriptions are model-visible text, so treat them as untrusted input too.

Name the one incident on record that wasn't AI at all, and why it belongs in an AI security review.
Show answer

Knight Capital, August 2012 — a deployment error activated dormant trading code with no circuit breaker or kill switch, costing ~$440M in 45 minutes. The canonical proof that unattended write access, not model intelligence, is the actual risk surface.
