Agent Memory

The model is rented, the memory is owned · memory

corehigh confidence2026-09-13

Hook

Every model call is stateless. Memory is entirely what the harness puts in the context window this turn — so it is a retrieval and token-budget problem, not a storage one.

Mental model

Ask three questions, never one: what is it, how do we find it, how do we maintain it. Collapsing them is where every confused memory argument comes from. The model is rented; the memory is owned.

Decide

Use when durable memory earns its place
  • The fact must survive across runs and no system owns it
  • An operator can inspect and correct what gets stored
  • Episodic logging already exists to derive it from
Skip when it is not a memory problem
  • A system of record already owns the fact authoritatively
  • It is this run's evidence or workflow state
  • No inspector and no delete path exist yet

Aryaka

SASE/SD-WAN support agent. Procedural: escalation policy, RCA template, "never propose a config change inside a customer's freeze window" — skills/.md in git, preloaded because omission is a compliance failure. *Semantic: per-customer topology, SLA tier, carrier mix, named contacts, standing preferences — one Postgres row per fact, with source and validity. Episodic: every ticket, RCA, change window and call summary, partitioned by month.

The gate is an event boundary, not a turn count: consolidate when a ticket closes. A ticket is the natural unit of "something is now durably true", and it is explainable to an operator in a way that "every 20 conversations" never is.

Assumption: ~20,000 semantic rows across 500 customers. Breaks when: nobody can open one view and read everything the agent believes about a customer.

Say this

Three questions, kept separate: what is the memory, how do we find it, how do we maintain it. Most designs collapse them — and maintenance is where memory systems actually die.

Trap

A vector database on day one. The tell: you named a product before counting facts — and 500 customers at 40 facts each is 20,000 rows, which is nothing, and small enough that a human could still read the whole thing.

Probe

Why must episodic memory exist before semantic memory?
Show answer

Semantic is derived from it — you cannot consolidate what you did not log. Building semantic first means hand-authoring facts, which is a demo rather than a system, and when you improve the consolidation prompt in month two there is no raw material to regenerate from. Episodic logging is also cheap and immediately useful: debugging artifact, replay fixture, audit trail, eval candidate and consolidation input — five uses from one change.

A stakeholder asks for "long-term memory." What five things hide in that word?
Show answer

Memory (an explicit customer preference), knowledge (a historical Salesforce case), evidence (the three cases retrieved for this alarm), workflow state (commands already run in this investigation), and trace (everything the agent did this run). Different owners, lifetimes and correctness bars. Most of what a stakeholder means is knowledge a system of record already owns authoritatively — see the enterprise-retrieval card.

The gate is set at every 100 conversations to save summariser cost. What breaks?
Show answer

The latency of learning. A customer states an escalation preference in conversation 3 and it does not reach semantic memory until conversation 100 — for 97 conversations the fact sits in an episodic log the agent does not search, so it behaves as if it never heard. Set the gate from how fast facts must become durable, then cost it. An event boundary beats a turn count because it is explainable to an operator.
