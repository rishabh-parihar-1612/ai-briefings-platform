Acceptance Evals — Beyond Correctness

Correct isn't the same as merged · evals › acceptance-evals

coremixed confidence2026-09-10

Hook

Correctness evals are automatable and saturable — that's exactly why they saturate. Mergeability asks a harder question: would a human actually accept this unedited?

Mental model

Correctness measures whether the output is right; acceptance measures whether the human downstream takes it as-is. The second is a strictly harder, non-saturating bar.

Decide

Use when a suite is worth its cost
  • Correctness metrics sit above ~90% and stop discriminating between two systems
  • A team can "feel" a quality difference no existing benchmark captures
  • A review tool already exists that could yield an edit/acceptance signal cheaply
Skip when defer, do not fake it
  • Correctness itself is still the bottleneck and hasn't been solved yet
  • No downstream human review step exists to measure acceptance against
  • The output type has no natural "accepted unedited" signal to instrument

Aryaka

The measurable version for the NetDevOps config-change agent is change-acceptance rate: of the config diffs it proposes, what fraction enter the change window untouched, with no engineer edit? Unlike a golden eval set, this needs no new dataset — it's instrumented directly from existing change-review tooling, and it moves for real reasons: a rewritten diff means the agent's syntax was fine but its judgment about what to change wasn't good enough to trust without a human rewrite. This sits alongside the existing groundedness/citation gate as a 4th, independent signal.

Say this

A benchmark score above 90% with an argument still ongoing about which model to ship is the signal to build an acceptance eval — mergeability, not correctness, is the axis still moving.

Trap

Treating a saturated correctness benchmark as proof the system is ready. The tell: the pass rate is high but the post-generation edit rate before something actually ships is also high — two numbers that should move together and don't.

Probe

Why does a correctness eval eventually stop being useful even if it never had a bug?
Show answer

It saturates — scores across systems cluster near the ceiling and the metric stops discriminating. Correctness is automatable, which is exactly what makes it saturable; the target doesn't move with the codebase, house style, or team convention the way acceptance does.

Your RAG-generated RCA passes every groundedness check. What's still missing before you'd trust the system?
Show answer

Whether the on-call engineer sends it to the customer unedited — an acceptance signal, not a correctness one. Groundedness says the facts are right; acceptance says a human downstream found it good enough not to rewrite, which is a strictly harder and more useful bar.

How do you instrument an acceptance eval without building a new golden dataset?
Show answer

Use the edit-distance-before-merge (or before-send, before-approval) signal already sitting in existing review tooling — a config-change acceptance rate, a send-unedited rate — rather than hand-labeling a new set. It's the cheapest acceptance proxy available and moves for real reasons.
