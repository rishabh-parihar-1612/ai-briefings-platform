Cloud-Native Coding Agents

The workspace decision rewrites security, review, and CI · cloud-coding-agents

supportingmixed confidence2026-09-13

Hook

Where a coding agent runs — laptop or disposable cloud sandbox — decides what security model is possible, what review means, and what size company you can run.

Mental model

Amp calls it an "orb": a disposable cloud sandbox running the agent's whole loop, not just the model. Moving execution off the laptop only pays off once the credential, review, and CI questions get redesigned around it too.

Decide

Use when blast radius is internal and rollback is proven
  • Internal tooling change; rollback is a redeploy under a minute
  • Many parallel variants are worth trying before picking a fix
  • Agent's own test run has been measured against CI for weeks
Skip when stakes or reversibility say no
  • Change reaches a customer-facing or hard-to-reverse production path
  • Rollback for this category has never actually been executed
  • "AI wrote it" is the whole argument, not blast radius

Aryaka

Aryaka's NetDevOps team lets engineers ask a coding agent to write and ship small automation scripts — config-drift checks, tunnel-health remediation — against the SD-WAN orchestration API's staging tier, in a disposable sandbox torn down after each run. Review is waived for staging-only and internal-tooling scripts, where rollback is a redeploy under a minute; it stays mandatory for anything reaching the production config-push path, because a bad push touches a customer's live network state, not an internal dashboard. Agent-run tests are the fast first pass inside the sandbox; a separate CI stage still gates production because "exhaustive" hasn't been measured for this codebase yet. Modeled cost: 15 tasks/day × 20 min × ~$0.15/hr ≈ $0.75/day in sandbox compute — trivial next to the real cap, the human-approval queue.

Say this

It's not "we trust the agent so we skip review" — it's mean-time-to-recovery over mean-time-between-failures, and it only holds where rollback is fast, tested, and the blast radius stays internal.

Trap

Waiving review or CI by authorship ("AI wrote it") instead of blast radius. The tell: nobody can name the measured MTTR or point to a rollback that has actually fired — only one that was described in a design doc.

Probe

Your team waives code review for agent-authored changes. What's the first question a good interviewer asks back?
Show answer

What's the blast-radius line — and has the rollback for that category actually executed once against real state, or only been described? MTTR-over-MTBF only holds if detection and rollback are proven, not assumed; Amp's own migration only counts because the rollback path fired for real on a live production change, not in a design doc.

Someone says "why do you even need CI if the agent runs its own tests?" What's the sharpest honest answer?
Show answer

CI's job was never "catch what a human missed" — it's the deterministic, exhaustive stage that runs regardless of what fit in anyone's context window, human or agent's. Quinn Slack's own objection to himself: "you don't trust the agent to be exhaustive" — it runs what's in its context, not necessarily everything the project needs.

A coding agent runs in a cloud sandbox with a token scoped to read-only production logs. Is that safer than a developer's laptop?
Show answer

Only if the token is scoped by resource AND time. A read-only token that never expires is still a live standing risk months later — the same as an unrevoked laptop credential. Amp's OIDC tokens expire (e.g. 30 minutes) whether or not the task finished, forcing re-authorization rather than assuming safety from "read-only" alone.
