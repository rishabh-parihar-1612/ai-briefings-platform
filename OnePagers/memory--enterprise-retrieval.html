Enterprise Retrieval

Don't start with a vector database · memory › enterprise-retrieval

Hook

"I don't want my agent to remember what Salesforce already knows — I want it to efficiently find, verify and reason over what Salesforce knows."

Mental model

Derived indexes are for discovery; systems of record are for truth. The projection is disposable and rebuildable, which is exactly what makes it safe to have one — so nothing may ever be true only in the projection.

Decide

Use when index it
  • High-volume historical data, hours-to-days freshness is fine
  • Strong structured fields exist to filter on first
  • The index can be rebuilt from an authoritative source
Skip when call it live
  • Alarms, device state, telemetry — seconds to minutes
  • Authoritative verification before an action
  • Permissions or deletions upstream would drift silently

Aryaka

Self-troubleshooting from an EE alarm. Ownership stated first: Salesforce owns cases, Jira engineering issues, Confluence the SOPs, EE the alarms, the devices their own state. CDC feeds one rebuildable projection — SQL, full-text, vector.

Trigger: a tunnel-flap alarm. System: normalize, retrieve the SOP branch (not all 50 pages), filter 10M cases to product=SD-WAN + subtype=Tunnel Flap + region=APAC, down the funnel to 20, compress to evidence records carrying root cause and resolution, then collect live device state. Hypotheses carry supporting and contradictory evidence, so the agent cannot converge on whatever it thought first.

Human sees: a recommendation behind a policy gate, or one of the 6 termination states. Breaks when: the product field has 40 spellings — metadata hygiene sinks these projects, not the ranker.

Say this

Derived indexes are for discovery; systems of record are for truth. The LLM decides what information is needed; deterministic infrastructure decides how to fetch it efficiently.

Trap

"Vectorize Salesforce and forget the source." The tell: you cannot say how a record deleted or access-revoked upstream stops being retrievable — inserts and updates any sync handles, and a revoked record that stays searchable is a compliance incident.

Probe

Live API or vector index for the case history?
Show answer

False binary. Live-only gives latency, API load, token cost and — the one that kills the product — unpredictable execution time. Index-only gives stale truth, sync complexity, hard invalidation, duplicate authority and permission drift. The resolution: the projection serves discovery, a live call serves authoritative verification, and freshness is decided per evidence type rather than once for the system. Publish a staleness SLO and keep a full-rebuild backstop.

Cases contain long email threads. Why not just embed the comment field?
Show answer

It flattens a timeline with authorship. An early customer claim ("we think it's the firewall") and the closing confirmed finding ("ISP packet loss") become indistinguishable after chunking, so the agent retrieves the disproven one and sounds certain. Keep author_type and thread_position on every chunk. And half the bytes are quoted reply chains, signatures and disclaimers — a naive parser attributes quoted text to the wrong author, inverting the exact signal you built.

What actually deserves promotion to durable memory?
Show answer

A much shorter list than people expect, and the shortness is the feature: explicit preferences, explicit instructions, confirmed recurring behaviour, validated troubleshooting invariants, and operational knowledge no system of record owns. Not "customer had packet loss on May 14" — Salesforce and telemetry own that. Everything during a run is workflow state and evidence, with the lifetime of the investigation. Promote only after validation, with provenance and expires_at.
